# 代理失败改直连一次，连续失败进冷却

有 `config.proxy` 时先走代理；传输层失败（`network` / `timeout`）改直连重试一次。代理连续失败 3 次后 60 秒内只直连，到期放行一次探测，成功即清零。降级状态写进结果头一行（英文单行，含重试间隔）。

理由：代理一坏，所有请求都撞同一个坏代理，没有第二条路可走；而目标场景（Clash / V2Ray 可随时开关）里，临时故障不该被记成永久状态。此前一次代理故障 = 本会话全部请求失败。

边界：

- 只在还没拿到响应时回退。拿到响应后的读体失败不回退——POST 重发会重复副作用。
- `http_status`、调用方中断、SSRF 命中都不回退：那不是代理的错。已知盲点：代理自己回 `502` / `407` 时会被当成目标错误，不回退。
- 每次尝试各有一份 `timeoutMs`，所以代理连不上时最坏延迟是两份超时的和（默认 60 秒）。
- 本机目标仍绕过代理，不参与计数。
- 状态按进程共享（`createHttpClient` 每次工具调用都新建，计数放 client 里永远到不了阈值），并按 `proxy` 串重置：换了配置就重新数。

gh 子进程走同一套思路：探测先带代理，失败就去掉代理复核一次（复核预算 `min(timeoutMs, 5s)`，这一步只用来分清真故障与代理假象），业务命令用走通的那条路的 env。

gh 侧多一条限制：代理在中间时的结论不能当定论。实测代理不通时，`gh auth status` 会输出 `The token in keyring is invalid.`——把网络故障说成凭据失效。所以带代理的探测结果一律不缓存，只有直连复核的结论才算；网络故障的结论同样不进缓存（缓存键带上代理）。

契约见 `http/route.ts`、`http/index.ts`、`handlers/github/gh.ts` 与 `test/http.test.ts`、`test/handlers/github.test.ts`。
